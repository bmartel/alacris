# AGENTS.md — working on Alacris itself

You are in the **Alacris library repository** — the source of the npm package
`@alacris/core`. This file is for changing the library. Follow it exactly.

> **There are two AGENTS.md files here, and they are not interchangeable.**
>
> - **This one** governs work *on* the library: `src/`, `types/`, `test/`,
>   `bench/`, `docs/`, `scripts/`.
> - **[`docs/public/AGENTS.md`](docs/public/AGENTS.md)** is a *product*. It is
>   published at <https://bmartel.github.io/alacris/AGENTS.md> for people
>   building applications *with* Alacris to drop into their own project root.
>   Read it before writing any component code — including the demos and docs in
>   this repo, which must model its conventions.
>
> Changing the public API means updating that file too. See
> [Changing the public API](#changing-the-public-api).

## What the library is, and what that forbids

Alacris is web components with signals and fine-grained DOM updates, in about
6 kB gzip, ESM-only, zero dependencies, no build step required. Every one of
those is a constraint, not a description:

1. **`src/` has no dependencies. Not one.** Not a dev-time one that sneaks into
   the bundle, not a polyfill.
2. **Size is public API.** `npm run build` re-measures and rewrites `SIZE.md`,
   and CI fails if the committed file does not match what the commit produces.
   A few hundred bytes for a real capability is usually fine; a few hundred for
   a convenience wrapper is not.
3. **Anything a small app would not use belongs in an add-on entry point**
   (`store`, `context`, `signal`), never in the core. Add-ons *import* the core
   and must never bundle their own copy — two copies means two reactive graphs
   and everything silently stops updating.
4. **There is no build step for development.** `src/` is plain ESM and the tests
   import it directly. Do not add tooling to make a change easier.
5. **No `eval`, no `new Function`, and the only HTML ever parsed is a tagged
   template's static strings.** That is what makes the Trusted Types policy
   sound.

## The map

```
src/                 the library — plain ESM, no dependencies
  signal.js          reactive core: signal, computed, effect, batch, root
  html.js            the compiler, bindings, keyed lists, each
  define.js          custom elements, props-as-signals, attribute coercion
  style.js           css, adoptGlobal, vars — interned stylesheets
  store.js           deep reactive proxy, selector
  context.js         W3C context-request protocol
  index.js           the public core barrel
types/               HAND-WRITTEN .d.ts — not generated, must track src/
test/                node:test on happy-dom (see the three layers below)
bench/               js-framework-benchmark ops vs hand-written keyed DOM
demo/                index.html and test.html, served by `npm run demo`
docs/                Astro + Starlight site, its own package
ui/                  @alacris/ui — design system package, published separately
starter/             usage example and install guide — not a published package
scripts/             build, size, serve, sync-docs
dist/                GENERATED and gitignored — never edit, never commit
docs/public/lib/     GENERATED by the build — the bundle the docs site imports
```

## The commands

| command | what it does |
| --- | --- |
| `npm test` | the whole suite on happy-dom — signals, rendering, lists, styles, store, context, security, the release config, the built bundle |
| `npm run build` | writes `dist/`, syncs `docs/public/lib/`, regenerates `SIZE.md` |
| `npm run typecheck` | compiles the type-level tests against the shipped `.d.ts` |
| `npm run size` | re-measures `dist/` without rebuilding |
| `npm run sync-docs` | rewrites pinned versions and quoted sizes in the tracked prose |
| `npm run demo` | serves the demo, the browser tests, the benchmark and Alacris UI on :5173 |
| `npm run bench:bundle` | production React / Vue / Solid / Svelte / Lit / Stencil into `bench/vendor/` |
| `npm run test:ui` | Alacris UI smoke tests in `ui/` |

The docs site is a separate package: `npm run build` in the root first (the site
runs the real bundle), then `npm install && npm run dev` in `docs/` — :4321.

## Invariants in `src/` — code that looks odd on purpose

Most of the strange code in this repository is strange because of a specific bug,
and the comment above it is what stops it being "simplified" back into that bug.
**Read the comment before changing the line.** These in particular:

- **`signal.js` — `notify` never flushes inline.** Every observer of a source
  must be marked before any effect runs, or a diamond dependency reads a stale
  branch. Effects go on the queue; `flush` drains it.
- **`signal.js` — link arrays start `null`.** Most signals are never observed and
  most computations have one or two sources; a thousand-row list builds several
  thousand nodes. Do not pre-allocate them back.
- **`signal.js` — `effectNode`/`rerun` exist for the renderer.** A binding swaps
  `fn` and re-runs in place rather than allocating a fresh node that leaks into
  its owner's child list. `rerun` returns `null` for a dead node; the caller must
  allocate.
- **`html.js` — templates compile once per call site**, cached on the strings
  array in a `WeakMap`. Nothing may build template strings dynamically or wrap
  `html` in a way that defeats that identity.
- **`html.js` — attribute setters are built once per template part** and shared
  by every instance. Only a genuinely per-instance concern (a child range, a
  modified listener) gets an object.
- **`html.js` — the SOLE optimization.** A child hole that owns its element's
  whole content writes `textContent` with no anchors. Three fewer nodes per hole
  is the difference between competitive and not on a large table.
- **`html.js` — delegated listeners live on the render root**, not the document,
  so detached containers work, `composed: false` events like `change` stay in
  scope, and a nested component does not fire twice.
- **`html.js` — `Each` snapshots the array tracked and diffs it untracked.**
  Without the split, one store write deep inside one row rebuilds the whole list.
- **`define.js` — `coerce(null, default)` returns `false` for a boolean.**
  Removing an attribute cannot mean "restore the default `true`". Consumers are
  told to always write `"true"`/`"false"`; do not work around it here.
- **`define.js` — teardown is deferred a microtask.** Moving a node reconnects it
  in the same task.
- **`define.js` — pre-upgrade property values are replayed** in the constructor;
  values assigned before upgrade otherwise shadow the accessors forever.
- **`store.js` — `__proto__` reads as `undefined` and writes are dropped
  silently.** That is prototype-pollution hardening, and the silence keeps
  `Object.assign(state, await res.json())` working. It is not a bug.
- **`store.js` — array mutators are batched.** `splice` shifts one element at a
  time; unbatched, observers see a half-shifted array with holes.
- **`style.js` — never emit `!important`.** It is the one inner declaration a
  consumer cannot override, and overriding is the whole point of `vars()`,
  `::part` and `adoptGlobal`.
- **`scripts/build.js` — the minifier options are load-bearing.**
  `booleans_as_integers` breaks the `v === true` / `v === false` attribute checks
  when a signal holds `1` or `0`, and only `_`-prefixed internals are mangled.
  Both are commented with what they cost and what they saved.

Internal properties are short (`p`, `s`, `d`) because they sit on hot paths.
Public names are spelled out in full.

## Tests — three layers, and which one you want

1. **`test/*.test.js`** on happy-dom — fast, and where almost every behaviour
   belongs. `test/setup.js` installs the DOM; run via
   `node --import ./test/setup.js --test test/*.test.js`.
2. **`demo/test.html`** in a real browser — for what a simulated DOM cannot
   express: custom-element upgrade, `adoptedStyleSheets`, real listener options,
   SVG layout. **If happy-dom disagrees with a browser, the browser is right**
   and the test goes here.
3. **`test/dist.test.js`** — guards the *built* bundle against minifier damage,
   and against an add-on ever bundling its own copy of the reactive core. It
   skips when `dist/` is absent, so run `npm run build` before trusting a pass.

Three more files are not about the library's behaviour and are easy to overlook.
`test/release.test.js` asserts the release config actually produces notes with
content (an empty-notes release shipped once). `test/security.test.js` installs a
Trusted Types stub before importing the renderer — which is why it must stay a
separate file, since `node --test` gives each file its own process. And
`test/docs.test.js` reads the real export list out of `src/` and enforces the
checklist below.

Writes are synchronous: assert immediately, never `await` a tick. Delegated
handlers only see events that bubble, so synthetic events need
`{ bubbles: true }`.

## Performance claims need numbers

`bench/` runs the standard js-framework-benchmark operations against
hand-written, keyed, delegated DOM — the floor — and against production React,
Vue, Solid, Svelte, Lit and Stencil (`npm run bench:bundle`). It verifies every implementation
renders byte-identical output before timing any of them; keep that check working
if you add one.

If a change is meant to be faster, include before/after numbers. If it trades one
operation for another, say which and why the trade is worth it.

## Changing the public API

A public API change is not done until all of these agree. `test/docs.test.js`
enforces 2, 4 and 5 mechanically — it reads the exports from `src/` and fails
naming what has fallen behind — but it can only check that a name is *present*,
not that what is said about it is true:

1. **`src/`** — the implementation.
2. **`types/*.d.ts`** — hand-written, not generated. `npm run typecheck`
   compiles `test/types.check.ts` against them.
3. **`test/`** — behaviour, plus the export list in `test/dist.test.js`.
4. **`docs/src/content/docs/`** — the guide *and* `reference/api.md`. Examples on
   the site are live: sources in `docs/src/demos/` are rendered as both the
   highlighted code block and the executed module script, from the same string,
   so they cannot drift from what a reader sees.
5. **`docs/public/AGENTS.md`** — the consumer instructions. It is shipped
   guidance, not a summary; a stale rule there produces wrong code in every
   project that downloaded it. It is also in the release's commit assets, so the
   release rewrites version pins inside it. An export an application author
   genuinely has no use for may go in that test's `UNDOCUMENTED` list instead,
   with a reason — the list is checked for stale entries too.
6. **`docs/public/llms.txt`** and `README.md` if the surface area changed shape.

## Nothing documents a version or a size by hand

<!-- sync-docs:ignore — this section explains the rule, so it must not be
     rewritten by the rule. -->

`package.json` is the only place a library version is set (`@alacris/core`);
`ui/package.json` is the only place a UI version is set (`@alacris/ui`).
`SIZE.md` is the only place a size is measured. Everything else is derived by
`scripts/sync-docs.mjs`, which scans every tracked text file:

- `@alacris/core@0.2` stays a minor pin, `@alacris/core@0.2.1` is rewritten in full — the
  shape of a pin is its intent, so it survives.
- Size tables are anchored on themselves: the header names the metrics, the first
  cell names the bundle.
- A figure loose in a sentence cannot be placed automatically, so it is *checked*
  instead — it must be currently true of some bundle, or the script fails and
  names the file.
- CI runs `npm run sync-docs -- --check` after regenerating `SIZE.md`. If it
  fails, run `npm run sync-docs`; do not hand-edit the number.
- A file that must name a version or a size in prose opts out with a
  `sync-docs:ignore` marker anywhere in it.
- `CHANGELOG.md` is never touched. It records what was true at each release.

## Commits decide the version

Releases are automated: every push to `main` runs semantic-release, which reads
the commits, publishes to npm via trusted publishing (there is no `NPM_TOKEN`
and there should never be one), writes the changelog, runs `sync-docs`, commits
back and tags. Nothing is versioned by hand.

`ui/` is a second package, **@alacris/ui**, with its own workflow, tags
(`ui-v*`), and changelog. Scope `ui` publishes that
package and is dropped from the library release. `starter/` is a usage
example and install guide; it does not publish. Do not mix `src/` and
`ui/src/` in one pull request.

So the commit message *is* the release note and must be a
[Conventional Commit](https://www.conventionalcommits.org/). `feat` is a minor,
`fix`/`perf`/`refactor`/`revert` are patches, `docs`/`test`/`build`/`ci`/`chore`
release nothing. **Pull requests are squash-merged, so the PR title becomes the
commit message** — CI fails a title it cannot parse.

Be deliberate with `!`: semantic-release does not special-case pre-1.0, so a
breaking change takes `0.x` straight to **1.0.0**. While the API is settling, use
a plain `feat:` and describe the change in the body.

Full detail, including how a release actually runs, is in
[CONTRIBUTING.md](CONTRIBUTING.md).

## Common mistakes (wrong → right)

| Wrong | Right | Why |
| --- | --- | --- |
| Editing `dist/` or `docs/public/lib/` | Change `src/`, run `npm run build` | Both are generated; `dist/` is gitignored |
| Generating `types/` from JSDoc | Hand-edit the `.d.ts` | They are authored, and `typecheck` tests them |
| Adding a helper to the core | An add-on entry point | The core is a size budget, not a junk drawer |
| An add-on importing its own core copy | Import `@alacris/core` | Two graphs, no updates, no error to point at |
| "Simplifying" odd code with a comment above it | Read the comment first | It is odd because of a bug the comment names |
| A perf change with no numbers | Run `bench/` before and after | Claims here are measured, not asserted |
| Hand-editing a size or a pinned version | `npm run sync-docs` | CI fails a stale figure |
| Changing the API without `docs/public/AGENTS.md` | Update it in the same commit | It ships to other people's agents |
| Mixing `src/` and `ui/src/` in one PR | Split them; scope the UI PR `ui` | They publish as different packages |
| `!important` anywhere | `vars()`, `::part`, `adoptGlobal` | It is the one thing a consumer cannot override |
| A PR title like "fix stuff" | `fix(html): keep focus when a keyed row moves` | The title becomes the release note |

## Verifying your work

Before declaring a task done:

1. `npm test` — including `test/dist.test.js`, which needs a build to be real.
2. `npm run build` — then confirm `SIZE.md` is either unchanged or committed with
   the change explained.
3. `npm run typecheck`.
4. `npm run sync-docs -- --check` if you touched any prose.
5. Anything a simulated DOM cannot judge — upgrade timing, adopted stylesheets,
   focus across a reorder — checked in a real browser via `npm run demo`.
6. `npm run build` in `docs/` if you touched the site; it fails on a broken
   internal link.
