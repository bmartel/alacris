Lists are where a rendering model is decided. Alacris gives you two, and the
difference between them is where the work lands.

## each

Every row gets its own reactive scope, built **once**:

```js
import { html, each } from '@alacris/core';

html`<ul>
  ${each(
    () => todos(),                                  // the source
    (todo) => html`<li>${() => todo().text}</li>`,   // one row
    (todo) => todo.id                                // identity
  )}
</ul>`
```

Three consequences, and they are the reason `each` exists:

- **Reordering moves nodes.** `insertBefore` on the rows that actually moved.
  Focus, scroll position, text selection and what the user typed all survive.
- **A changed row wakes only itself.** Rows are not rebuilt and neighbours are
  never consulted.
- **Appending touches nothing else.** Matching runs at the head and tail, so a
  push never looks at the rows already there.

### The row is a signal

`row` is a signal, so read it inside a thunk to keep the binding live:

```js
each(items, (row) => html`<li>${() => row().text}</li>`, (r) => r.id)
//                                  ^^^^^^^^^^^^^^^^ live
```

Writing `${row().text}` instead would read once and never update. That is
occasionally what you want — for a field that genuinely never changes, it is
one less subscription.

### The index

Ask for a second parameter and you get the index, also as a signal, kept current
as rows move:

```js
each(items, (row, i) => html`<li>${() => `${i() + 1}. ${row().text}`}</li>`)
```

It is only created if you ask for it.

### Identity

The third argument decides what "the same row" means. Without it, rows are
matched by the item itself, so a new object is a new row:

```js
each(items, render)                    // identity: the item reference
each(items, render, (item) => item.id) // identity: the id
```

Use a key whenever your data is replaced rather than mutated — which is most of
the time with plain signals. With [the store](../state/), rows are mutated in
place and reference identity already works.

### Create it where it runs once

`each` keeps its state as long as the *same* `each(...)` value stays in place —
which it does when the template is built once, in `setup`. Inside a re-run
thunk, every run calls `each(...)` again, and a fresh spec tears the whole
list down and rebuilds it:

```js
html`<ul>${each(() => rows(), renderRow)}</ul>`          // built once — rows persist
html`<ul>${() => each(() => rows(), renderRow)}</ul>`    // rebuilt on every run — don't
```

The source is already a function, so there is nothing reactive to gain from
the outer thunk — pass `each(...)` directly as the child value.

## Mapping the array yourself

For a short, stable list, a plain `.map` is fine, and `keyed` gives items a
stable identity:

```js
import { keyed } from '@alacris/core';

html`<ul>${() => items().map((i) => keyed(i.id, html`<li>${i.text}</li>`))}</ul>`
```

<Aside type="caution" title="It does not scale">
A `.map` rebuilds every row's template result on every change, so the renderer
has to walk all N rows to discover that one moved. On a thousand rows a swap
is **1.43 ms** with `.map` and **0.102 ms** with `each`.

Reach for `each` past a few dozen items.
</Aside>

## Nesting

`each` nests, and inner lists react independently of outer ones:

```js
html`<div>
  ${each(
    () => groups(),
    (group) => html`
      <section>
        <h3>${() => group().name}</h3>
        ${each(() => group().items, (item) => html`<li>${() => item().label}</li>`, (i) => i.id)}
      </section>`,
    (g) => g.id
  )}
</div>`
```

## Rows with several roots

A row does not have to be a single element. Multi-root rows are bracketed
internally and move as a unit:

```js
each(items, (row) => html`<dt>${() => row().term}</dt><dd>${() => row().def}</dd>`)
```

## What it costs

From the [benchmark](../../reference/performance/), against hand-written keyed
DOM, JS and DOM mutation only:

<table class="bench">
  <thead>
    <tr><th>operation</th><th>vanilla</th><th>`.map`</th><th>`each`</th></tr>
  </thead>
  <tbody>
    <tr><td>append 1,000 to 10,000</td><td>2.50</td><td>10.0</td><td>**6.20**</td></tr>
    <tr><td>update every 10th row</td><td>0.030</td><td>0.385</td><td>**0.090**</td></tr>
    <tr><td>swap 2 rows</td><td>&lt;0.01</td><td>1.37</td><td>**0.110**</td></tr>
    <tr><td>remove a row</td><td>&lt;0.01</td><td>0.365</td><td>**0.055**</td></tr>
  </tbody>
</table>

Pair `each` with [the store](../state/) and `update every 10th` stays around
0.090 ms in this harness (row objects are replaced). The store's win is
in-place mutation of deep fields, where the list is never re-diffed at all.
